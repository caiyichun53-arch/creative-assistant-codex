# 创作助手技能标准

## 使用时机

当用户要求新增、拆分、审查或改写创作助手技能时使用。包括:

- 把现有流程拆成更小的技能。
- 新建 `.agents/skills/<技能名>/SKILL.md`。
- 检查某个技能是否符合本项目要求。
- 判断一个能力应该做成技能、脚本、子代理还是普通文档。

## 目标

把创作助手能力写成可被不同代理复用、可执行、可验收的技能合同。当前技术载体是 Codex 本地技能目录和 `SKILL.md`,但正文不能只写给 Codex 看,必须让任何能读取文件和执行命令的代理也能照着完成任务。

技能只保存工作方法和执行边界,不保存具体创作经验。经验继续存放在本项目的 SQLite 数据库和 Obsidian 经验库。

## 官方技术要求

- 每个技能必须是一个目录,目录内必须有 `SKILL.md`。
- `SKILL.md` 顶部必须有 YAML 信息头,且只要求 `name` 和 `description`。
- `name` 使用小写英文、数字和连字符,保持短而清楚。
- `description` 是触发入口,必须写清什么时候使用、什么时候不要使用。
- 技能正文只在触发后读取,所以不要把触发条件只写在正文里。
- 技能要专注一个工作,不要把多个大流程塞进一个技能。
- 需要稳定执行、写文件、写数据库或跑工具时,优先调用确定性脚本。
- 技能可以有 `scripts/`、`references/`、`assets/`,但只在确实需要时创建。

## 本项目固定边界

- 技能负责判断、分支、调用顺序和验收。
- 脚本负责确定性动作:建目录、写配置、写数据库、采集、判定、保存、校验。
- 子代理负责特定角色执行,例如写手或项目审查顾问。
- `AGENTS.md` 负责项目宪法和硬边界,不要把它复制进每个技能。
- 经验不写进技能正文,也不散落在各技能目录。
- 经验存放位置:
  - SQLite: 状态、账号、选题、草稿、改稿对照、语感经验、原子内容。
  - Obsidian 经验库: 人设、范例、方法论、语感燃料、真人写作基石。

## 技能正文结构

不要机械填模板。技能正文只写执行者真正需要的信息;某一项没有实际作用时可以省略,不要为了完整而填空。

建议保留的核心项:

```text
# 中文技能标题

## 使用时机

## 目标

## 输入

## 执行步骤

## 输出

## 合格检查

## 禁止事项

## 失败处理
```

按任务需要增加的项:

```text
## 依赖
## 可读取参考
## 是否回写经验
## 多领域适配
```

判断规则:

- 没有外部脚本、数据库、目录、工具要求时,不要写“依赖”。
- 没有必须让代理阅读的材料时,不要写“可读取参考”。
- 技能完全不涉及经验沉淀时,可以把“是否回写经验”合并进禁止事项或输出边界。
- 技能不涉及领域切换时,不要硬写“多领域适配”。

## 字段写法

### 使用时机

写用户会怎么说,以及系统处在哪个阶段时触发。不要写泛泛的“用于优化流程”。

### 目标

用一句话说明这个技能完成的闭环。目标必须能验收。

### 输入

只列本技能真正会使用的输入。不要为了“以后可能用”塞可选输入。

每个输入都必须说明用途。没有用途的输入要删除。

### 依赖

只列缺了就无法执行本技能的东西,例如确定性脚本、数据库表、配置目录、产物目录、外部工具。项目说明文件不是执行依赖。

不要把 `AGENTS.md`、`BUILD_PLAN.md`、`CLAUDE.md` 或同类项目章程写成可迁移技能的必备依赖。它们最多是当前项目的边界参考;不存在时不能阻断一个可复用技能。

### 可读取参考

只有当“代理必须先理解某份外部材料,才能做判断或生成结果”时才写这一项。它不是固定栏目。

适合放进“可读取参考”的例子:

- 写作、审稿、改稿技能需要读取材料包、任务合同、用户人设、待处理正文。
- 项目审查技能需要读取被审查范围内的关键文件或证据包。
- 经验提炼技能需要读取待提炼的改稿对照、评论样本或已认可稿。
- 脚本参数不确定、脚本失败、验收失败时,按需读取脚本说明、数据库结构或日志。

不应该放进“可读取参考”的例子:

- 为了熟悉项目而读取账号配置、人设文件、目录结构。
- 脚本已经封装了写文件和写数据库,仍要求代理读样例配置再执行。
- 当前技能根本不用某份材料,但为了填栏目把它列上。
- 写“读取整个经验库”。

如果没有真正需要读取的参考,直接省略“可读取参考”这一节。

### 执行步骤

步骤必须能落地。凡是写“判断”“检查”“确认”,都必须写清后续动作:

- 如果判断为 A,下一步做什么。
- 如果判断为 B,下一步做什么。
- 如果无法判断,停在哪里,问什么。

需要脚本时写清脚本路径、参数和调用后检查项。

### 输出

写清产物名称、路径、格式和状态。不要只写“完成”。

### 合格检查

用“通过 / 警告 / 失败”逐项检查。任一关键项失败时不得进入下一阶段。

### 禁止事项

写防漂移红线。禁止事项要具体,不要写“不要乱来”。

### 失败处理

写清缺输入、缺文件、脚本失败、经验不足、权限不足时怎么停止和回报。

### 是否回写经验

必须明确:

- 不回写经验。
- 只写候选经验。
- 可晋升经验。
- 只登记审查结果。

经验回写只能写入本项目规定的 SQLite 或 Obsidian 位置。

### 多领域适配

写清哪些来自领域配置,哪些是通用逻辑。不得因为新增领域而复制一套代码。

## 命名和中文说明

- 技能 `name` 用英文短名,例如 `create-domain-account`。
- 中文标题和正文用中文。
- 避免中英混杂。必要术语要首次解释。
- 项目术语统一:
  - `brief` 写作“材料包”。
  - `hit` 写作“爆款视频记录”或“爆款库条目”。
  - `draft` 写作“草稿”。
  - `diff` 写作“改稿对照”。
  - `hook` 写作“开头钩子”。
  - `workflow` 写作“流程”。
  - `validator` 写作“校验器”。

## 技能与经验的关系

技能只能规定如何取用经验,不能把经验正文长期写死进去。

允许写:

- 从 `vault/真人写作基石.md` 读取相关片段。
- 从 `language_fuel_insights` 按领域、阶段、强度取少量经验。
- 从 `vault/范例/<类别>/` 取少量已晋升范例。

禁止写:

- 把大量范例复制进技能正文。
- 把禁词、硬约束塞进生成提示。
- 把某个领域的经验当成所有领域规则。
- 让技能自行全库检索后自由发挥。

## 审查清单

新技能交付前必须检查:

- `SKILL.md` 有 `name` 和 `description`。
- `description` 写清触发和不适用范围。
- 正文只包含执行者真正需要的信息,没有机械填空。
- 输入都被执行步骤实际使用。
- 执行步骤里每个判断都有后续动作。
- 输出和合格检查可执行。
- 如写了可读取参考,每个参考都有明确用途;无实际用途的参考已删除。
- 禁止事项具体。
- 经验存放仍走本项目 SQLite 和 Obsidian。
- 不把确定性动作交给模型自由决定。
- 不复制大量项目章程或经验正文造成上下文膨胀。
