# 内容业务核心包｜完整设计基线

## 1. 目的和裁决原则

本文件是重新开发内容业务核心包的唯一业务设计依据。它定义系统做什么、谁作决定、正式数据如何形成，以及各项业务怎样衔接。

系统把可追溯的真实素材转成用户可判断的内容机会，支持研究、口播内容生产、人工确认以及文案和音频交付。质量、事实边界与用户判断优先于数量和自动化。

### 1.1 设计目标与现有代码的关系

设计不是现有代码的说明书。设计确定完整产品应具备的业务能力；代码只表示其中哪些已经实现。每项能力都必须标明状态：

- **已实现**：当前保留代码已经提供该能力；
- **待开发**：设计需要，但当前代码尚未实现；
- **外部依赖**：能力需要保持可用，但由项目外工具提供；
- **明确剔除**：不属于内容核心，不应作为核心包能力保留。

清理代码时，只能删除“明确剔除”的能力，或已经被替代的实现；不能因为一项设计还未实现就从设计中删掉它。

### 1.2 当前能力总表

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 真实素材采集 | 外部依赖 + 已实现接入 | 核心包保存来源和标准化结果 |
| 本地音频转写 | 外部依赖 + 已实现接入 | 用于把外部素材转成研究前可读文本 |
| 素材筛选、候选选题和用户选择 | 分段实现，尚未完整验收 | 对标、标签、历史信号、问题拓展和用户方向已有入口；候选评分仍在重审，热点暂停 |
| 正式选题、研究方案和人工确认 | 已实现骨架，主链未完整验收 | 正式链路按版本保存，候选选择和直接下题可以进入研究方案 |
| 深度研究、证据整理和内容生产 | 已实现骨架，质量和接通程度待验收 | 已有受控输入、模型调用和版本链；尚无完整真实主链闭环 |
| 经验、偏好和复盘 | 分层实现，发布反馈尚未正式启用 | 已有人工确认的经验入口和发布反馈基础；不能因正式库暂无记录判定能力不存在 |
| 文案生成音频、声音配置和音频审核 | 已实现接入 | 最终稿绑定已确认声音配置，经本地 VoxCPM2 分段生成、技术检查、SenseVoice 回听核对和人工审核后才形成正式音频交付 |
| 任务排队、自动重试、内部工人领取和开发自检 | 明确剔除 | 由执行型智能体平台或开发环境承担，不属于内容核心 |

### 1.3 主链成熟度的统一口径

本基线不再用“有没有正式数据”代替能力状态。主链每个节点都分别记录：正式目标设计、设计文档对齐、代码实现、模块验证、主链接入、端到端验收、正式启用，以及未启用原因。未启用原因必须说明是上游尚未走到、尚未实现、已实现但未接通、尚未验收、主动暂停、设计重审，还是其他明确原因。

“候选选题”是通过最低资格判断、可以继续比较的题目；“正式候选”是完成必要排除、合并、评分和排序后提供给用户选择的候选；“正式选题”是用户明确选择后进入生产计划的题目；“真正研究”只从正式选题之后开始，负责资料搜集、事实确认、补材料和深入研究。四者不能互相替代。

## 2. 系统目标与边界

核心包服务多个内容账号，完成：

1. 收集和整理真实素材；
2. 发现、筛选并呈现候选选题；
3. 在用户选择后完成研究和证据整理；
4. 设计内容路线、生成、修改和确认文案；
5. 形成文案和音频正式交付；
6. 把经过用户确认的有效经验沉淀为后续创作参考。

核心包不负责视频剪辑、对外发布、评论区运营、商业转化，也不提供逐句改写、同义替换或洗稿能力。

真实采集工具和本地转写能力是外部依赖。核心包只受控调用它们、接收标准化结果和保存必要业务材料。

## 3. 分工与人工决定权

| 参与方 | 负责的事 | 不负责的事 |
| --- | --- | --- |
| 用户 | 选择选题、确认研究方向、审核稿件、确认交付、确认经验 | 手工维护复杂数据关系 |
| Agent 平台 | 理解用户自然语言、延续对话、发起允许的业务动作、安排耗时工作并汇报结果 | 自行改变既定流程、跳过确认、直接改正式状态或写正式数据 |
| 核心包 | 保存正式事实、校验关系和版本，并依据当前状态决定允许进入的下一步 | 替用户决定做什么内容或是否发布；接受 Agent 绕过流程的直接写入 |
| 模型 | 理解材料、提出候选、归纳研究、生成和审阅文字 | 决定业务状态、直接写正式数据、自动扩展范围、替换模型配置 |
| 外部依赖 | 提供真实来源、公开材料和转写结果 | 决定选题和正式业务结论 |

用户可以在任何业务节点选择通过、退回、暂缓、拒绝、取消或亲手修改。任何重要修改都形成新版本，历史不被静默覆盖。

不论用户从飞书、界面或其他入口进入，均由 Agent 把指令交给同一个核心包。核心包只按已确认流程允许状态变化；Agent 和模型可以提出建议或请求动作，但不能决定状态变化是否成立。这样既保留自然对话，也保证既定流程不会因 Agent 的临场判断而偏离。

## 4. 账号、领域和素材资格

账号是独立内容主体，各自拥有受众、表达偏好、已发布表现和长期方向。一个账号的结论不能自动套用到另一个账号。

领域规定可讨论的对象、应避开的内容、研究证据要求和风险边界。领域可共享流程，不能丢失自身边界。

素材只有同时满足以下条件，才适合进入候选判断：

- 来源可追溯；
- 与目标账号或领域有关；
- 能说明具体问题、对象或冲突；
- 有研究和讲述空间；
- 没有无法处理的事实、版权或内容风险。

一个热点标题、对象名称、单条视频或标签本身都不是正式选题。

新建领域的正式冷启动输入固定为：一个领域、一个自营账号和 20 个对标账号。此前出现的初始领域描述、10—20 个对标账号、30 个对标账号等内容，统一视为旧版本设计、旧实现、旧配置或旧运行痕迹，不再作为当前产品规则讨论。历史记录可以保留，但下一次新领域冷启动不能继续按这些旧规则放行。

这 20 个对标账号的成熟度足够，是用户人工寻找和选择对标账号时的输入前提，不是系统自动筛选账号的准入步骤。系统默认用户提交的 20 个账号满足该前提，不自动替换账号或寻找第 21 个账号；平台历史正常耗尽但成熟样本仍不足 20 条时，只记录真实不足状态，不降低标准、不换号、不伪造基线。

对标账号首次注册先读取该账号最近 90 天内的视频，第一阶段正式近期样本最多保留 50 条，且不因成熟样本达到 20 条提前停止；超过50条时只为到达90天边界继续翻页，额外近期视频不进入正式近期样本。第一阶段到达90天边界或平台正常耗尽后，若正式近期样本中的成熟视频不足20条，才沿当前分页位置向更早内容读取并补足，第二阶段补到20条成熟样本即停止，不再通过重新从头请求500条来补足，最终正式保留和计算仍不得超过50条。平台正常耗尽仍不足20条时记录明确不足状态并停止后续基线和爆款筛选，异常失败仍按失败/可继续机制处理。满 7 天的视频进入成熟历史基线；未满 7 天的视频作为过渡样本保留、每日更新并参加当日爆款判断，满 7 天后才进入成熟历史基线。成熟历史爆款有两条入口：第一条是评论数与点赞数之比至少 20%，达到即直接入选；第二条是先满足点赞数至少 20000，再满足任一互动指标达到自身成熟历史中位数 3 倍。互动倍数路径不因账号较小而改用其他点赞门槛。扩展后成熟历史仍少于 20 条时，不产生历史倍数爆款，但评论点赞比仍可直接入选。日常正式新视频按 D0—D7 留存；已有 20 条完整且在发布后 36 小时内发现的序列后启用正式 D 基线，之后使用最近 50 条完整序列；正式 D 判断为任一指标达到同观察点中位数 2 倍，或任意两个指标分别达到 1.6 倍。不得使用四分位距异常值算法，不得设置 35% 等爆款入选率阻断。正式写入入口必须重新校验采集策略、首次保留上限、扩展条件、三类首次接触、基线集合、判断通道和入选集合；校验失败时自动阻断后续备料、拆解和模型调用。

账号成熟度单独按成熟历史基线判断：成熟历史样本不足 20 条时，账号状态为“新账号”，不启用历史互动倍数通道，但评论点赞比达到 20% 仍可直接入选；成熟历史样本达到 20 条时，账号状态切换为“成熟账号”，才启用历史互动倍数通道。账号注册了多久、账号总共有多少条视频，以及正式 D 序列是否达到 20 条，都不改变账号成熟度。正式 D 基线是另一项能力，只决定日常新视频能否按 D0—D7 的同位置数据判断。三类首次接触标签只说明视频是怎样被发现的，不代表账号状态，也不代表视频已经完成观察。

每日由一次统一自动触发启动当天各正式领域的日常工作。每个正式领域、每个业务日期各自拥有一个正式 daily run，正式身份为 domain + business_date；所有领域 daily run 共用一个执行槽并严格串行。failed 或 stopped 的领域不自动重试，释放执行槽后其它领域可以继续；用户之后继续时恢复同一领域、同一业务日期的 daily run，只处理未完成部分。completed 才表示该领域当天日常完成，当天所有领域是否完成由各领域 daily run 状态推导。不存在全局 daily lifecycle、父子 daily run、partial_completed 总状态或第二套全局业务状态；通知状态不参与 daily run 状态判断。任何对标账号完成正式建库后立刻加入日常追踪；以后新增领域或账号自动并入，不另建定时任务。修改一次运行时间，对全部已接入领域同时生效。领域尚未完成整套冷启动时，只完成追踪和留存，不提前生成该领域的候选。

自营账号也必须进入持续采集，但它与对标账号的观察用途不同：自营账号用于保存自己发布的内容表现，并建立自己的同期表现基线；对标账号用于发现和拆解外部内容。两者必须分开保存、分开计算，不能因为自营账号暂时没有真实发布记录，就把这项设计判定为不存在。

实施和运行必须使用同一份可执行业务契约。实施代码发生变化时，项目钩子自动核对正式设计、契约和代码；真实服务启动以及采集、基线、爆款正式写入时，运行钩子再次核对同一契约。任一层不一致都必须阻断，不能只提醒后继续。

任何已经确认错误的正式业务结果，都必须从当前正式数据及全部下游产物中彻底删除，不建立“旧结果保留、纠正层覆盖、必要时恢复”的双轨机制，也不允许任何流程回退读取。合法的原始采集材料可以继续作为重新计算基线的输入，但被判定无效的爆款资格、备料、拆解、标签证据、归纳和其他派生产物必须同时清除。系统只保留一条既定路线和一套当前有效结果。

## 5. 素材、发现与候选选题

### 5.1 发现入口

常规发现入口分成两层：日常对标内容先只做持续追踪和爆款判断；只有进入正式爆款库的历史存量爆款或日常新增爆款，才进入候选筛选。其他候选来源是达到单条点赞 10000 门槛且排除已登记对标账号的标签结果、绑定正式母来源的问题拓展，以及用户保存的方向。热点当前暂停。所有来源先处理资格、重复、领域关联、时效和风险，再把少量合格材料交给语义判断。

问题拓展不是独立素材来源，也不是已经成立的候选选题、研究问题、核查结论或最终标题。它的业务含义是从正式爆款拆解中发现的、绑定母来源的拓展内容线索；必须保留正式母来源类型和编号，母来源不能是另一条问题拓展。拆解完成后，原始拓展线索先经过自动轻量资格化，只检查最低前提、可获得材料、问题级领域内容承载和独立不重复价值；通过后才进入现有候选判断、评分和用户选择，未经资格化的线索不得直接展示给用户。资格化达到值得继续研究就停止，已取得的合法来源、链接、基础材料和摘要供后续正式研究复用，但不提前形成研究结论。

用户明确下达“直接作为正式选题”时，可以跳过候选记录。直接下达至少要明确服务账号和领域、核心问题以及本次范围或要求；用户指令本身必须作为该选题的来路留存。它不受候选评分、每日前 10 或每日数量限制约束，但仍要核对与已有选题的重复或关系，并在记录中明确已有材料、尚缺材料、时效和风险。用户给出的方向、线索、链接或不够精确的想法不属于直接下达，仍先补充信息或形成候选。

人物、单个对象和对象集合是通用的特殊探索入口，不因用户直接给出就自动成为正式选题。人物进入人物探索；单个对象进入作品或对象探索；一组对象进入集合盘点探索。探索由 Agent 围绕对象、相关背景和用户问题开展判断，取得能支撑具体讲述的可追溯材料。集合盘点必须先说清共同问题或盘点角度；只有对象清单、没有共同理由时，只是方向，需要补清。用户给出的集合只是研究起点，不是锁死的最终范围；发现某个对象不合适时，Agent 在对话中说明情况和建议，由用户决定是否删掉或替换。最低数量、专属平台、目标时长和其他材料要求由当前领域配置决定，不能把某个领域的规则自动套到其他领域。研究可以形成排序作为参考，但不自动变成最终排名；默认不排名，确有需要时才采用排序。没有明确领域规则的探索必须先停住，不能猜测或继承旧规则。

凡是用户亲自给出的方向、链接、人物、对象或对象集合，都必须先保留为人工手动提供的来源和原始内容；“来源于用户”不等于“已经成立正式选题”。信息不全时可以进入补充、人物探索、对象探索、集合盘点或候选，但后续每一步都要保留这条人工来源，不能因为改变了处理路径而丢失。

人工手动来源只说明选题或探索为什么从这里开始，不是内容事实的依据。后续取得的研究材料另行保留为事实依据；两者同时关联，不互相覆盖，也不得把用户的输入误当作事实证明。

对象探索的硬标准只有：有明确的核心问题、足以支撑目标内容形式的可靠材料，以及清晰的讲述方向。目标时长和材料门槛由领域规则或用户明确要求决定；材料不足时，Agent 应如实说明缺口或停止，不能用空泛感想凑成内容。问题拓展不得由内容类型集合决定领域资格。领域允许/排除、材料和风险规则是唯一领域门禁；历史已出现内容类型只用于整理、检索和减少同义分类。拓展检查可以在没有历史内容类型集合时进行，只要问题有正式母来源、明确未解决增量、符合当前领域边界并足以独立成篇。已有类型语义匹配时优先复用；确有新的合法内容形态时允许使用新的简洁类型名称，但类型名称本身不扩张领域规则，也不构成新能力批准。音乐娱乐领域的具体 domain_context 另行规定：拓展最终必须主要由音乐、作品或音乐人物的音乐经历承载；仅因人物、作品或机构与音乐有关，却把主体转成制度、法律、技术、商业、职业制度、纯私生活或泛娱乐知识的，不通过。具体查哪些材料、如何组合材料和怎样判断讲述效果，交由 Agent 在自然对话中处理，不设跨领域固定公式。

对象探索在正式研究之前，用于判断是否值得讲、讲什么并保留已取得材料。用户确认正式选题和研究方案后，正式研究按方案推进，并在合适时复用已有材料，避免无意义的重复采集；具体怎样检索和补充由 Agent 判断。

作品探索通过后，Agent 以判断最强的方向为主，并可简短提示其他可行方向；用户通过自然对话决定采用、调整或补充。用户确认的方向才形成正式选题，不把这些对话选择拆成固定的平行流程。

### 5.2 素材与热点处理

每份素材应保留来源、取得时间、原始标识或链接、领域关联、摘要、可用范围和风险说明。临时下载的视频或音频在确认转写后不作为长期正式资产保留；保留来源信息、转写文本和必要元数据即可。

明显重复的热点或同一事件先合并。热点标题不足以证明事实或领域关系；需要正文时，只能在允许范围内补足可追溯材料。

热点只是公共选题主链的一种来源。热点专属部分只负责采集原始热点、保存原始数据、标准化标题、去重、初步事件合并、保留代表来源、读取正文详情和保存来源元数据。从热点形成真正的候选问题开始，必须进入公共的资格、候选生成、合并、评分、正式候选和用户选择链，不再保留“热点专用机会判断 → 热点专用候选生成 → 直接写候选池 → 热点专用评分”的平行流程。当前热点主动暂停，历史记录保留；恢复前必须单独验证来源和规则。

### 5.3 候选选题

每个候选需要明确：

- 要讲的核心问题；
- 相关受众及其关切；
- 内容增量，不是简单复述；
- 一个主要讲述角度；
- 已有材料与仍缺的材料；
- 时效、事实、相似和表达风险；
- 值得用户考虑的原因。

用户可以选择、拒绝、暂缓或要求换角度。被选择的候选成为正式选题，未选择的候选不会自动进入研究；用户明确直接下达的正式选题按上一节的例外处理。不设通用的每日选择数量硬上限；候选池通过来源前置筛选、同题同角度合并、维度评分排序和人工选择来控制优先级。评分只对去重后的候选卡执行，不对原始视频逐条生成候选；没有合格候选时可以为零。

候选评分当前不视为最终方案。旧评分已经实现并运行过，但曾出现真实候选大量得到同一分数的问题；第一轮证据映射修复后分布有所拉开，仍有明显趋同。当前结论是“评分设计重审中”：最终目标仍为 0—100 分，既不能靠粗糙档位制造固定分数段，也不能为了分散制造没有依据的伪精度；不得为评分新增昂贵全网搜索，不重复奖励资格阶段已经保证的条件，也不以评分强迫选题滑向固定的解释、科普或专业分析方向。最终评分必须以后续真实发布结果校准。本轮不冻结新公式、不冻结新权重。

### 5.4 同题与相似风险

系统应识别相同问题、相近角度和父子关系，优先补充已有选题。引用对标内容时，必须区分围绕同一问题的独立重构和由来源引出的独立拓展。

无论哪种，都必须重新核查事实、形成独立观点和独立叙事；不得形成逐句改写路线。

## 6. 正式选题、研究与证据

### 6.1 正式选题

正式选题是用户确认后可以进入研究方案的内容方向，至少关联核心问题、受众关切、来路、时效、风险、与其他选题的关系和用户决定。候选转入时保留候选及其支持材料；用户直接下达时，保留用户指令、当时已给材料或“尚未提供材料”的明确状态。用户指令只证明“为什么做这个题”，不能代替后续研究中的事实依据。

### 6.2 研究方案

研究前先形成方案，写清核心问题、待检验观点、关键主张、证据要求、材料边界、允许查找的方向、停止条件和已知风险。

用户确认方案后才开始研究。退回方案时创建新版本，不覆盖旧版本。

### 6.3 研究结果

研究按“主张—证据关系”组织。每条关键主张要说明它是事实、解释、推断还是待验证观点；它的重要性；支持、反对或限制它的材料；以及争议和不确定性。

同源转载不能当成多份独立证据。材料很多但不能形成有解释力、可讲述的新理解时，不能进入内容生产。关键结论无法证明时，应缩小结论、补充材料或取消。

正式研究使用外部网页、文件和允许的研究材料；当前代码明确不把视频、音频、转写、评论或视频平台链接当作正式研究来源。它们只能停留在发现和素材环节，不能越过研究边界。

研究输出包含可成立的结论、证据关系、材料台账、限制和可行内容路线。用户确认研究结果后，才进入内容计划。

### 6.4 内容路线

同一选题只有存在实质创作分歧时，才保留少量不同路线。不同路线可共享研究基础，但都必须有材料支撑。用户选定路线后，才生成正式内容计划。

用于比较的路线文本不是正式稿件，不进入交付或经验学习。

## 7. 内容生产与人工审核

### 7.1 主链

> 常规材料或用户方向 → 候选 → 用户选择；或用户明确直接下达正式选题 → 自动形成研究方案 → 用户确认研究方案 → 深度研究 → 用户确认研究结果 → 内容计划 → 用户确认计划 → 初稿 → 用户确认初稿 → 优化 → 定向修改 → 审核 → 用户确认最终文案

每一步只产生紧邻下一步所需产物。未经用户确认的产物不能作为下游正式输入。

### 7.2 内容计划

内容计划应说明核心承诺、目标受众、核心结论、叙事路线、开头与推进、段落功能、主张与证据对应关系、不确定性、风险，以及本次考虑、采用或拒绝的经验与偏好。

创作输入发生冲突时，按以下顺序裁决：

1. 已确认的事实边界和硬性禁项；
2. 用户当前对本次任务的明确要求；
3. 已确认的内容计划；
4. 账号长期偏好；
5. 有证据支持的经验；
6. 通用写作提示。

### 7.3 初稿、优化与用户改稿

初稿必须能追溯到内容计划、研究主张和证据。新增关键事实要回到研究或计划补足，不能直接混入稿件。

优化关注叙事吸引力、推进、口播节奏、信息密度、材料组织和领域贴合。定向修改必须定位具体问题，不能虚构用户经历、立场或情绪。

用户亲手改稿形成新版本，是理解账号表达偏好的重要材料；单次临时改动不能自动变成长期规则。

### 7.4 审核和最终确认

审核至少确认：关键事实是否有依据，结论是否越过证据边界，内容是否兑现核心承诺，叙事与口播表达是否成立，是否存在相似风险或不当引用，实际采用的经验是否仍适用。

审核结果应明确为通过、局部修改、需要重写、回到研究或取消。最终稿必须由用户确认。

## 8. 音频与交付

用户确认最终文案后，完整产品应支持使用已保存的声音配置生成音频，并把文案、标题、声音配置和音频版本关联为一份交付内容。

音频审核确认声音是否合适、内容是否完整、是否与最终文案一致。仅有音频问题时可以重新生成；发现事实、立场或文案边界问题时，应退回对应上游环节。

本地转写只用于把外部素材变成可研究的文本，不是文案转音频能力。文案转音频现由独立的本地 VoxCPM2 接口执行：只接受用户已确认的最终标题、口播正文和声音配置；长文本按段生成并保留元数据，生成后执行音频技术检查和 SenseVoice 回听文本核对，再交用户审核。仅有音频问题时退回重新生成；发现事实、立场或文案边界问题时退回内容审核环节。用户批准音频后才形成正式交付；系统不生成视频，也不代替用户发布视频。

## 9. 外部发布、数据回流与 P0—P7

内容生产主链在音频交付结束，但正式设计还包含一条独立的反馈链：音频交付版本 → 用户手动登记外部视频 → 用户确认实际发布版本是否与批准版本相同 → 系统读取获授权数据 → P0—P7 观察 → P7 复盘和反馈候选。批准版本和实际发布版本必须保留两种身份；如果实际发布内容不同，不能只把它当成批准版本的别名，至少要保留差异事实和可追溯的实际发布版本依据。

系统不生成视频、不剪辑视频、不自动发布、不自动发送；外部发布必须由用户完成。系统只负责保存用户确认的发布关联，并读取、记录和分析获得授权的发布后数据。P0—P7 与对标账号的 D0—D7 分开保存，不能混算。

P7 先保存真实数据和缺失情况，再区分选题、叙事、材料组织和外部条件，最后才形成待用户确认的经验或实验结论。一次表现不能自动改写长期规则，也不能自动跨领域套用。

发布反馈分三层：第一层是反馈基础，保存上游判断、版本、发布身份、表现快照和基线关系；第二层是反馈观察，统计评分与表现、资格通过后的研究失败、内容类型长期表现和不同来源的投入产出；第三层是自动反馈优化，例如自动调评分权重、修改资格规则、淘汰内容类型或停止来源。当前只保留前两层的设计和受控人工反馈入口，第三层不建设。

当前反馈链是设计保留、实现状态单独验收的后续阶段；不得因为当前尚未完成实现，就把设计要求改写成“系统不需要”。

## 10. 系统范围边界

系统只负责内容文案、音频交付，以及用户确认后进入的外部发布登记和授权数据反馈。视频生成、视频制作、对外发布和评论区运营不属于系统能力。

## 11. 经验与长期偏好

系统分开保存三类内容：

| 类型 | 含义 |
| --- | --- |
| 经验 | 什么机制在什么条件下可能有效，以及风险和失效条件 |
| 内容偏好 | 用户或账号偏爱的表达、方向和风格 |
| 反馈与证据 | 用户改稿、实际采用、复盘和人工判断 |

经验必须有适用范围、条件、证据、风险、状态和版本。内容计划只使用当前任务真正相关的少量经验，并记录采用或拒绝的原因。

用户改稿和人工复盘可以形成经验反馈，但不能自动改写长期规则。经验的新增、升级、暂停、恢复、拆分或合并必须由用户确认。

### 10.1 对标拆解与经验进入

对标拆解一条视频一条留存，只服务口播文案和内容打法。冷启动阶段的内容类型只记录观察结果；只有经过用户确认并冻结的类型，才可作为正式生产分类。不得把多条拆解自动压缩成“大家通常都这么做”的领域经验，也不得把高播放量当成文案有效的证据。对标拆解必须先区分原文明确陈述的信息、作者观点/评价和意义判断、评论中新出现且待核实的事实说法、模型不得自行推导的新事实或因果。原文明确陈述的信息可以作为原文叙事前提分析，不要求本节点重新核查；作者观点按观点和解释框架分析；评论新增事实只能形成待核实拓展线索；不得把原文同时出现的 A、B 自行写成 A 导致 B。分析以内容承诺、推进与兑现、核心交付/内容增量和关键内容动作为主，不使用固定技巧清单强制所有样本产生脚本公式、情绪曲线、人设、反常识或万能模板。评论只能描述实际评论者的回应、共鸣、追问、争议、补充或未满足需求；评论与正文内容点呼应不能写成“印证”或“证明”了内容选择有效、策略成功、内容唤起了某种情绪或形成了核心共鸣，也不能推出高表现因果；输出前要复核并改写这类效果或因果表述。不同内容类型按实际内容发动方式调整分析重点；人物/事件、作品背景、盘点/集合、解释、观点和混合内容可以使用不同分析视角，但仍由同一通用拆解能力完成，不为每个领域或类型复制完整流程。source_content_type 只保存一个主导内容发动方式，不为次要观点、盘点或经历创建长复合类型；observed_content_types 只保存规范主类型，且绝不是领域白名单。

单条拆解可以形成带来源的候选复用原则，但只能说明本篇具体动作、当前作用、最低必要前提和明显误用风险；它不能因为来源是爆款就证明机制有效，也不能直接升级为领域经验或账号经验。内容增量可以表现为新事实、新关系、新解释、新观点、新分类/策展方式、新情绪理解或其他真实交付；没有可靠对照材料时，不得假装知道全网共识，也不得为了传播性强造反常识。

拆解短板只能相对于本篇自身内容承诺、实际推进和当前内容类型目标判断；不得因为本篇没有采用另一种内容类型的能力，就把它判断为缺点。没有明确的承诺落差、推进问题或当前类型内部缺陷时，可以明确写无明显短板。

用户不需要记住“整理经验”这句话。内容计划确实需要新的可复用经验、且已有具体拆解足以支撑一个带来源和边界的候选时，系统才主动给出一份短提醒。用户确认一次后，经验进入正式库；日后实际创作会自动引用相关的已确认经验，不再逐次打扰用户。未确认前，拆解仍只是可检索的单条材料。

## 11. 正式数据与版本关系

正式数据至少覆盖账号与领域、来源与材料、候选与选题、研究、内容与音频交付、经验与偏好。

每个正式对象必须能回答：它从哪里来、当前有效版本是什么、谁何时作了什么决定、影响了哪些后续内容，以及是否存在风险、暂停或更正。

会改变内容含义、事实、研究结论、审核结论、配置或用户决定的修改，必须创建新版本。正式数据只能经核心业务入口写入；模型输出、外部采集结果和远程编辑都要先校验、建立版本并保留差异。

## 12. 模型与外部材料规则

模型只用于明确的语言理解、素材分类、关系判断、候选判断、研究方案、证据提取、深度分析、内容计划、写作、优化、语义审核、经验提案和实验复盘。模型必须按明确配置运行，不自动换模型、换服务或降级。

模型输入只包含当前任务所需的正式材料、用户要求、领域规则和必要上下文。模型输出必须经过结构、引用、范围和状态校验，不能直接写正式数据或改变正式状态。

网页、评论、转写和用户文件都是外部材料，不是系统指令。密钥、登录信息和个人数据不得进入内容正文、研究结论或非授权位置。

## 13. 交互范围与重新开发底线

业务交互应围绕六个区域：自营账号与表现、对标与发现、选题与研究、内容与交付、经验与复盘、必要配置。

远程入口可以用于提醒、查看、通过、退回和提交修改意图，但不能形成第二套正式数据。远程编辑必须回到核心包形成正式新版本。

重新开发必须守住：常规发现先有真实来源和清楚问题，再有候选；候选由用户选择，或由用户明确直接下达正式选题后，自动进入研究方案；研究方案经用户确认后，才做深度研究；先有证据，再写作；先由用户确认最终稿，再交付；先有授权表现和复盘，再沉淀经验。

### 13.1 执行型智能体平台与核心包的边界

研究、写作、审核和经验归纳都应被拆成原子业务能力。执行型智能体平台负责按用户动作调用这些能力、安排执行顺序、承接运行失败和再次执行。

核心包只负责：读取和校验正式输入、形成正式版本、保存用户决定、保护上下游关系和写入正式数据。核心包不保存内部任务队列、不管理工人领取、不进行自动重试或超时恢复。

### 13.2 历史技术模式说明

此前曾存在一种“技术闸门模式”：经验提案在进入正式经验前，需要若干开发自检结果。该模式只保留为历史说明，不再参与业务运行，也不用于判断某条经验更好或更差。

经验尚未被真实业务反馈证明时，应明确标为待验证假设；有实际采用和表现材料后，仍由用户判断是否在指定条件下采用、暂停或修改。技术检查不能替代真实反馈和用户判断。
### 问题拓展的固定来源

问题拓展的生产时点固定在“爆款拆解完成时”，不是拆解完成后再从评论区另起一条流程。拆解输入包括爆款口播原文和评论，且两者都必须实际传给拆解模型；原文是主要依据，评论只用于补充观众疑问、争议和未满足需求。每条拆解先识别并保存本条实际采用的内容类型；内容类型只是归类记录，不另设一套质量凭证或证据门槛。问题拓展检查是每次拆解的必做步骤，但允许结果为空。每个拓展必须同时满足：有可定位的母来源锚点；母内容尚未回答且存在新的独立内容交付；必须针对拓展问题本身的核心内容重新执行领域门禁，符合当前领域允许/排除和风险边界；具有足够明确的核心问题与讲述承诺，可独立成篇；与母内容及本次其他拓展不重复。门禁要看拓展问题准备交付的核心内容是否仍在当前领域内；如果问题核心内容是领域主体在领域外的活动、职业或生活经历，除非领域规则明确允许，否则不得通过；如果不能从领域规则中指出该问题核心的明确允许依据，必须放弃拓展。母内容的领域资格、人物身份、对象关联或历史类型集合都不能代替问题级领域判断。仅仅与同一人物、歌曲、作品或主题有关，或者“还能继续讲一点”，不足以成立。拆解输出的原始拓展仍只是绑定母来源的线索；完成拆解后必须先自动轻量资格化，通过后才进入候选判断和用户选择，未通过的线索只保留简短 rejection_reason，不展示给用户。资格化只判断最低前提、可获得材料、问题级领域内容承载和独立不重复价值，达到值得继续研究就停止，不提前做正式研究。

原文明示或清楚涉及但未展开的对象、原因、后果、关系、经历、作品、事件或问题可以形成待验证拓展；评论可以补充与原文明确相关的追问、质疑、反例、补充、共同记忆或另一解释，但评论不能脱离母内容创造新方向，也不能把未经核实的事实说法直接变成事实结论。拓展问题可以扩大调查范围，但不能自行升级来源已经提供的事实前提；不得把一次合作预设成重大影响或历史意义，不得把评论提到的若干作品预设成被大众忽视或经典，也不得把普通经历自动包装成重大转折、行业影响或普遍现象。这项约束同时适用于拓展问题和拓展理由；需要后续研究才能成立的内容，应保持为开放问题或明确的待核实假设，不能在理由中补回未经来源支持的结论。涉及评论事实时只形成待核实问题；如果当前只有评论说法而没有足以通过最低前提和材料门槛的依据，待核实本身不构成资格化通过条件。拓展线索不继承母内容类型；母来源只说明线索从哪里来，子线索可以选择当前领域允许的其他主导内容类型。内容类型仅用于归类。优先复用本领域历史拆解中语义匹配的已有规范主类型；没有合适类型时，只要拓展本身通过领域门禁，可以使用新的简洁自然中文类型。历史类型集合不是领域白名单，不得因为 exact match 要求强行归入错误类型；新类型名称也不自动扩张领域规则。母样本本身明显命中领域排除项时，不产生问题拓展，其类型不得自动加入该领域历史类型集合。

每条拆解最多保留 3 个真正不同的具体问题；拓展结果只保留内容类型、具体问题和拓展理由，不另设逐条原文或评论凭证；其来源由这条正式爆款拆解的母来源关系保证。只有资格化通过的线索才允许进入候选来源读取和候选池，失败线索只留内部 rejection_reason。这样候选池看到的是“爆款拆解产生且通过最低资格的线索”，而不是一堆评论或脱离材料的猜想。
## 2A 内容类型生命周期补充（2026-08-18）

内容类型的正式生命周期固定为：冷启动观察 → 归纳候选类型 → 用户确认 → 正式冻结 → 正式生产只读取冻结类型。历史拆解中的 observed content type 仍是冷启动观察材料，不是生产白名单；旧 canonical keyword mapping 也不是批准事实源。领域配置中的 content type registry 才保存人工确认后的生产类型。registry 为 NOT_FROZEN 或 DRAFT 时，只能 DISCOVER/观察，不能把自由命名结果当成正式生产类型；registry 为 FROZEN 后，PRODUCTION/CLASSIFY 只能消费其中的 canonical id，无法匹配时返回 NO_MATCH 或 OUT_OF_SCOPE。

当前代码已经具备“保存观察类型”和“正式生产读取冻结类型”的边界，也已经有冻结注册表的局部验证；但还没有证明从新冷启动样本归纳候选类型、交给用户确认并形成冻结版本的完整业务闭环。因此，现有音乐领域的冻结注册表不能被反推为每个新领域都已经完成了内容类型冻结。

这条生命周期规则只约束内容类型的发现权和分类权，不改变冷启动的拓展、资格化和候选生命周期。新链路先保存 expansion signal，再投影到已批准类型；没有投影的 signal 不进入新的资格化。旧 question_expansions 保留兼容读取，但不允许在 production/classify 中绕过批准类型投影。

## 2B 领域生产边界补充（2026-08-19）

领域生产边界只回答“什么性质的问题属于这个领域愿意生产的范围，什么不属于”；它不回答“内容怎么讲”。内容怎么讲由正式冻结的内容类型负责。生产边界不能退化成人物、作品、事件等题材清单，而要抽象成能够适用于未来新题材的生产原则。

冷启动样本用于提供证据并暴露真实分歧，市场样本不自动等于用户最终定位。只有真正影响未来生产范围的结构性选择才交给用户确认；领域生产边界也必须在用户确认后冻结。当前目标设计已经明确，但新冷启动样本归纳、用户确认和正式冻结尚未完成，不能把现有领域描述或历史题材清单当成已冻结的最终边界。

### 2B-1 每条拆解的边界观察（2026-08-27）

每条 competitor breakdown 在同一次拆解模型调用中可以额外产出一条可选的 `boundary_observation`。它只记录本条样本对“什么性质的问题可以做、什么性质的问题不应该做”提供的新增自然语言证据；没有新增边界信息时可以省略。该观察不是最终生产边界、内容类型、问题拓展 signal 或正式规则，不新增表、阶段或第二次模型调用。生产边界候选只聚合当前运行成功拆解中的 `source_id/source_ref` 和非空 `boundary_observation`，不重新读取完整 `analysis_text`、`expansion_signals`、`question_expansions` 或 `typed_expansion_leads`；最终原则仍须通过现有来源追溯、人工确认和冻结流程。

生产边界候选只是人工决策辅助材料，不是正式确认的强制前置；即使当前冷启动没有候选，用户仍可通过同一既有人工确认入口提交明确的生产边界内容，由 Core 直接写入正式冻结版本。该直接提交必须保留明确的人工作为来源，不得伪装成模型候选或自动确认。
