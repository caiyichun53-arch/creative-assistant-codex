## 阶段2：Work 非正式质量验证

状态：不是正式业务上线闸门；如有需要，单独做人工质量测试。

### 纠正后的事实

- 用户使用的是 GPT 桌面客户端中的 ChatGPT、Work 和 Codex，不是单独登录的 Codex 命令行客户端。
- 之前尝试的命令行应用服务测试不代表 GPT 客户端，因此它的“未登录”和“服务不可用”结果不能作为用户 GPT 订阅不可用的结论。
- 之前新增的命令行 GPT 测试入口已经撤掉，避免形成错误的第二套模型路径。
- 当前项目还没有证明“本地业务核心可以直接调用 GPT 桌面客户端当前对话或 Work 会话”的正式连接方式。

### 正确测试范围

- 使用用户实际登录的 GPT 桌面客户端中的 Work 或明确指定的 GPT 客户端工作方式。
- 只读取一条音乐领域已完成口播素材和对应爆款拆解。
- 只请求生成一份隔离测试初稿。
- 不写入正式数据库、正式稿件版本、正式状态或音频。
- 不自动重试，也不切换 Hermes。

### 下一步

如果以后要评估 Work，再单独确认它与本地业务核心的连接方式，并由用户判断创造力、自然度和工程腔。这个评估不改变正式 Hermes API 路线。

## 当前放行结论

正式业务保持 Hermes API 路线，不建立模型选择器，不开启正式自动运行。

## GPT 桌面客户端与 Work 验证结果

- 官方能力边界确认：Work 适合研究、分析和多步骤成果，Codex 适合代码、终端和项目开发。
- GPT 桌面客户端的 Work 在获得权限后可以使用本地文件和桌面应用。
- Work Local 与 Codex Local 是分开控制的，不能因为 Codex 可用就推断 Work 已接通。
- 当前项目没有发现已经验证通过的 Work 本地业务工具连接。
- 当前项目仍残留一条命令行客户端接入配置，只能作为待清理的旧路径，不能作为 Work 的实现。

结论：Work 暂不作为正式内容生产入口。它最多作为单独的人工质量测试方式；正式业务仍由 Hermes API 处理，正式数据仍由业务核心保存。

## 已确认的运行分工

这是用户已经确认的当前架构方向，不代表连接和模型切换已经完成：

- 正式研究、爆款拆解、写稿和改稿统一沿用 Hermes API 业务模型路线。
- 用户通过已有人工入口完成领域、素材、任务状态、人工确认和版本决定；完整冷启动第一批把“领域 + 账号 + 20 个对标账号 → 预检查 → 一次确认 → 自动创建运行”接入既有人工决定接入层，不绑定独立网页或其它具体交互载体。
- Work 可以单独用于人工质量测试，但在连接和质量验证完成前，不写正式数据，也不替代 Hermes。
- MCP 暂不建设，只有手动传递资料被真实业务证明为障碍时再评估。
- Codex 只用于项目开发和维护，不参与正式内容生产。
- 正式业务不同时使用 Work 和 Hermes 处理同一任务。

## 本阶段下一步

继续沿用 Hermes API 推进正式业务。Work 和 MCP 暂不进入正式链路；只有未来真实出现人工传递资料的障碍时，才单独评估最小连接层。正式数据、状态和版本仍只经过同一个业务核心保存。

## 主链成熟度校准（2026-08-19）

本文件中的“正式库当前没有正式稿件、音频或发布登记结果”，只说明真实生产主链尚未走到这些节点，不代表对应设计或实现不存在。当前代码已经有正式选题、研究方案、内容生产版本链、音频交付、外部发布登记、P0—P7 观察和 P7 人工反馈的分段能力，但尚未完成从新建领域冷启动一路到真实发布的端到端验收。

当前新建领域输入已经统一为“领域 + 自营账号 + 20 个对标账号”。旧的 10—20 个、30 个和初始领域描述只作为历史痕迹处理，不再作为当前正式入口规则。第一批已完成并封板；2B-1、2B-2 和最终修正版 2B-3 已完成分阶段实现和隔离验证，但第二批整体隔离验收尚未开始。对标账号成熟度足够是用户人工寻找和选择 20 个账号时的输入前提，系统不自动筛选、替换账号或寻找第 21 个账号；平台正常耗尽后仍不足 20 条时只暴露真实不足状态。当时的候选评分尚未收口；该状态已被 2026-09-08 的唯一评分设计取代。

当前下一阶段统一为“第二批整体隔离验收”，不进入 2B-2、2B-3 或第三批。完整冷启动仍未完成：内容类型和领域生产边界尚未分别完成样本归纳、用户确认和正式冻结，标签或拆解结果不能单独触发冷启动完成。
