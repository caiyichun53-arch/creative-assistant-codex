# 冷启动实施阶段

## 业务结果

用户一次提交一个领域、一个自营账号和 20 个对标账号后，系统自动推进对标注册、首次历史采集、账号基线、历史爆款筛选、整版领域话题标签、爆款备料和逐条拆解；3B-1完成内容类型闭环，3B-2完成领域生产边界候选、既有人工决定入口整版确认和独立冻结资产接线，3B-3完成统一 `cold_start = completed` 判断。拆解只服务口播文案和内容打法；观察到的类型不自动变成正式生产类型，领域边界也不从标签或旧领域描述产生。注册过程不设置逐账号、逐步骤或逐标签人工确认。

## 当前第一批已实现边界

第一批只负责新领域进入冷启动：领域零状态检查、领域和账号引导、严格 20 个对标账号校验、一次用户确认、启动前最终契约检查，以及自动创建本领域当前唯一冷启动运行。成功运行保存本次输入快照和当前冷启动契约版本。

引导草稿、待确认配置和失败尝试不计入正式领域初始化。启动失败必须返回原因、清理未启动的正式配置并允许重新开始。一个外部平台账号只能属于一个领域；同步时发现跨领域账号必须拒绝，不能覆盖原领域。

本批不启动真实采集，不处理基线、爆款筛选、备料、转写、评论、拆解、内容类型确认、领域生产边界、候选、评分、热点或反馈。

## 当前第二批实现与整体隔离验收状态

第一批之后，2B-1、2B-2 和最终修正版 2B-3 已完成代码实现及对应的隔离验证；第二批整体隔离验收也已通过，第二批正式封板。整体验收使用临时数据库和外部边界替身，没有写入正式泛科普数据。

- 2B-1 已把当前运行接入 20 个账号的自动总编排，并把爆款筛选进度与备料、评论、转写、拆解进度分开记录。20/20 个账号完成爆款筛选后，标签输入立即齐备，不等待拆解。
- 2B-2 已在上述交接点自动生成当前运行的整版领域标签库：只读取合格爆款标题规范字段中来自平台原始标题或原始描述的实际话题标签，确定性过滤、统一、去重和统计来源；不读取拆解、转写、评论，不调用模型。整版审核走既有人工决定入口；账号注册严格按历史采集→基线和高信号筛选→备料→拆解推进。
- 2B-3 已按两个阶段采集首次历史：最近 90 天最多保留 50 条，成熟达到 20 条不提前停止；第一阶段真正结束且成熟不足 20 条时，才沿当前游标向更早历史补足到 20 条，最终正式留存不超过 50 条。旧的从头请求 500 条路径已退出正式冷启动。
- 3B-1 已完成内容类型闭环：只从当前冷启动运行的成功拆解读取观察类型，确定性汇总候选并保留来源追溯；通过既有人工决定入口一次整版确认后，写入生产读取的同一正式内容类型注册表。该闭环不读取旧历史、其它运行或其它领域数据，不调用模型，也不触发 `cold_start = completed`。
- 3B-2 已完成领域生产边界隔离闭环：只从当前冷启动运行的有效拆解读取事实，形成抽象、可追溯、可判断未出现新题材的候选原则，经既有人工决定入口一次整版确认后冻结为独立生产边界资产；正式生产读取同一冻结资产，缺失时阻断。该闭环不读取标签、内容类型或历史数据，不调用第二套人工系统，也不触发 `cold_start = completed`。
- 3B-2 细化：每条 competitor breakdown 在原本同一次模型调用中可选产生 `boundary_observation`；生产边界候选只聚合当前运行成功拆解的非空观察及其 `source_id/source_ref`，不重新读取完整拆解正文或问题拓展 signal，不新增第二次模型调用。
- 生产边界候选只是人工决策辅助材料，不是正式确认的强制前置；没有候选时，用户仍可通过同一人工决定入口提交明确的生产边界内容，由 Core 直接冻结正式版本，且记录来源为明确人工决定。

第二批整体隔离验收及 3B-1、3B-2、3B-3 项目隔离回归均已通过；这不等于第三批整体隔离验收已经完成，也不等于新版泛科普已经正式启用。当前下一阶段统一为“第三批整体隔离验收”，本轮不自动进入整体隔离验收。

## 当前确认规则

- 当前平台只做抖音。
- 当前新建领域冷启动固定登记 20 个对标账号；此前出现的 10—20 个、30 个或其他数量只作为旧版本设计、旧配置或历史运行痕迹保留，不作为下一次新建领域的放行条件。历史已经登记的账号不因本轮文档修正被删除。
- 对标账号成熟度足够是用户人工寻找和选择这 20 个对标账号时的输入前提；系统默认用户提交的 20 个账号已满足该前提，不做机器自动成熟度准入、自动替换账号或自动寻找第 21 个账号。平台历史正常耗尽但成熟样本仍不足 20 条时，只真实暴露不足状态，不降低标准、不换号、不伪造基线。
- 每个账号首次读取最近 90 天内最多 50 条；未满 7 天的视频保留为过渡样本并每天更新，满 7 天后才加入成熟基线。
- 第一阶段先获取最近 90 天内的视频，正式近期样本最多保留 50 条；这一阶段不因成熟样本达到 20 条而提前停止。最近 90 天超过 50 条时，为到达时间边界可以继续翻页，但超过50条的额外近期视频不得进入正式近期样本集合。
- 第一阶段到达 90 天时间边界或平台正常耗尽后，才重新计算正式近期样本中的成熟数量；不足 20 条时，沿当前分页位置向更早历史补足，补到 20 条成熟样本即停止。此前“重新从头请求 500 条”的路径不再用于正式冷启动；平台正常耗尽仍不足 20 条时只记录明确不足状态，不进入基线和爆款筛选，异常失败仍按原有失败/可继续机制处理。
- 成熟历史基线按账号自身、按互动指标分别取中位数。
- 成熟历史爆款有两条独立资格通道：
  - 任一互动指标达到自身成熟历史中位数 3 倍；
  - 评论数与点赞数之比达到 20%。
- 互动倍数通道必须同时满足点赞数至少 20000；评论点赞比通道不受点赞数门槛限制，也不设置小账号替代门槛。
- 正式 Hermes 创建冷启动时，以当前 Hermes 模型作为唯一默认来源，并在本次执行创建事务中保存模型、供应源和调用地址引用；同一次 executor 生命周期内只读这份执行绑定，运行中不热切模型。停止或失败后恢复同一 run 时，重新读取本次可信 Hermes runtime 的当前模型并更新现有 run_model，再启动新的 executor；已完成条目继续跳过，未完成条目使用本次新执行绑定。只有用户明确指定本次模型时才允许覆盖；业务配置中的分析、写作或拆解默认模型不得静默覆盖。测试和维护入口只能显式注入隔离模型。
- 未满 7 天的过渡样本不进入成熟基线，但必须每天更新并参加当日爆款判断；其过渡身份和观察日必须留存。
- 日常新视频采用 D0—D7：首次发现不晚于发布后 36 小时，完整观察序列达到 20 条后启用正式 D 基线，之后使用最近 50 条同观察点序列；正式 D 判断为单指标 2 倍，或任意两个指标分别 1.6 倍。
- 不使用四分位距异常值算法，不设 35% 入选率阻断，不把评论点赞比降为辅助标记。
- 页面总爆款入选率固定为“合格爆款数 ÷ 正式保留历史视频数”；成熟基线样本数只用于基线计算，不得充当页面入选率分母。
- 所有领域共用同一套爆款规则，不按音乐娱乐或社会生活另写一套。
- 20/20 个对标账号完成采集、基线和爆款筛选后，标签输入立即齐备；系统只从合格爆款的标题或平台原始描述中提取实际存在的话题标签，做确定性过滤、统一和去重，不调用模型；整版标签库由用户一次删改审核；标签分支不等待逐条拆解完成，但账号注册本身仍按历史采集→基线和高信号筛选→备料→拆解的阶段顺序推进。
- 内容类型按“冷启动观察 → 归纳候选类型 → 用户确认 → 正式冻结 → 正式生产只读取冻结类型”推进。3B-1 已完成当前运行范围内的观察汇总、候选保存、既有人工决定入口整版确认和同一正式注册表冻结；观察类型不自动升级，候选和冻结结果保留当前运行及来源追溯。
- 领域生产边界只回答愿意生产什么性质的问题，不负责规定内容怎么讲；它不能只列题材，必须抽象成可适用于未来新题材的生产原则，并在用户确认后冻结。3B-2 已完成当前运行范围、候选归纳、既有人工决定入口、独立冻结资产和正式生产读取的隔离接线；3B-3 已完成统一 `completed` 判断。新版泛科普实际资产仍需由真实新冷启动产生。
- 人名、组合名、机构名、节目名和作品名等命名实体使用领域内可维护的确定性词表过滤；规则更新后，尚未审核的整版标签库必须自动重新过滤并彻底删除命中的正式待审标签，不调用模型，也不保留恢复层。
- 爆款备料为每条合格爆款保留原视频、转写、前 60 条合格一级评论和来源关系；逐条拆解独立执行，单条失败只影响该条，不整包重做。
- 中断后继续同一步时，正式完成凭证必须绑定本次实际完成的整套结果；新增完成项不能复用旧请求编号，已完成项也不能重复写入。
- 每次自动注册、人工正式决定和资料库正式凭证写入前，都必须重新核对当前小型契约；服务启动后契约发生变化时，旧进程必须阻断正式动作并等待按新契约重启。
- 服务进程绑定整份当前冷启动契约；已落盘的采集结果只绑定采集相关规则，爆款筛选结果只绑定采集与筛选相关规则。暂停恢复、界面或知识镜像等无关规则变化不得把历史采集和爆款结果误判为失效。旧结果缺少分范围凭证时，必须按当前对应规则完整重算并一致后才可继续。
- 不得从多条对标拆解自动归纳、自动写入或自动启用“领域经验”。单条拆解保持独立、可检索和可追溯。
- 被确认不合格的爆款及其备料、拆解、标签证据和归纳必须从正式结果中彻底剔除，不保留恢复层、旧结果回退或兜底读取。
- 冷启动完成不依赖自动经验归纳。以后只有经用户确认的新经验才进入可读经验库；标签库、采集运行、模型日志、内部编号和完整追溯记录不得导出为知识页面；原始正式材料仍只保留在系统内用于必要追溯。

## 人工决定权

- 用户只负责最初提交冷启动配置、整版标签库删改审核、整版候选内容类型确认、整版候选领域生产边界确认，以及未来新经验的单次确认。
- 这些审核不得变成逐账号或逐条操作，也不改变账号注册的阶段顺序。

## 完成条件

- 正式人工交互载体能够返回真实阶段、真实分子和分母、最近心跳、当前账号或当前作品、失败原因和可恢复动作。
- 中断后按已完成条目续跑；重复来源去重；失败的残缺临时材料清理后重建。
- 普通进程中断在服务恢复后自动续跑；已经明确失败并暂停的账号或最终归纳必须把暂停状态留到重启后，不能借重启自动重试，只有用户点击继续才清除对应暂停。
- 某项工作成功后必须立即删除它此前的暂停记录；重启时若正式进度已经越过暂停发生的步骤，旧暂停记录必须作为失效状态清除，不能重新套回已完成工作。平台风控造成的明确暂停也必须落盘，不能借重启丢失。
- 旧进程因检测到冷启动契约已经变化而产生的暂停，只用于阻止旧代码继续正式写入；新服务成功加载当前契约后必须自动清除这类“等待按新契约重启”的暂停并续跑，不得再要求用户手工恢复。采集、模型和平台风控等真实业务失败不适用这一自动清除。
- 同一步分批完成或中断续跑时，不会因请求编号冲突卡死，也不会把旧的残缺结果当成完成。
- 冷启动的采集、筛选、备料、逐条拆解和标签库只是阶段结果；只有同一当前运行的前序必要结果满足、整版标签审核通过、内容类型和领域生产边界分别完成样本归纳、用户确认和正式冻结后，统一判断才会自动幂等标记冷启动完成。标签审核或标签加拆解完成本身不得单独触发；不增加第四次人工确认，也不自动进入候选、评分、研究、热点或反馈。
